# Dungeon Logic Campaign v1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the first real Dungeon Logic campaign loop: five manually curated campaign snapshots, linear persistent progression, Level Select, campaign-aware GameScene completion/onboarding, preserved dev launch paths, and deterministic generated-candidate promotion.

**Architecture:** Add a campaign subsystem above the existing puzzle runtime. Campaign content is source-controlled static `LevelDefinition` snapshots; campaign state is normalized against a manifest and persisted behind an async storage boundary. Boot resolves dev query launches first; otherwise it initializes `CampaignService`, opens `LevelSelectScene`, and launches `GameScene` with an already-resolved level plus campaign/dev context. Promotion remains dev-only and is the only path from `.generated` candidate reports into runtime campaign content.

**Tech Stack:** TypeScript 6, Phaser 4.2, Vite 8, Node 26 typings, `tsx` sanity scripts, browser `localStorage` fallback. No custom backend and no Yandex SDK adapter in this slice.

**Spec:** `docs/superpowers/specs/2026-09-07-campaign-v1-design.md`

## Global Constraints

- No custom backend, private HTTP API, custom database, server account system, custom cron jobs, or server-authoritative economy/gameplay.
- Do not add Yandex-specific storage to Campaign v1; keep `CampaignProgressStorage` async so a later Yandex adapter can replace local storage without changing progression logic.
- Do not change puzzle rules, `LevelValidator`, Puzzle Solver behavior, Human Solver behavior, Difficulty Analyzer scoring/bands, or Generator Difficulty v2 behavior.
- Do not move, rename, or promote `src/data/levels/level001.ts` through `level012.ts`; they remain technical authored/regression content.
- Production campaign runtime must never read `.generated`.
- Campaign v1 content uses only Monsters and Treasure Rooms; no Blockers or Directional Doors in campaign snapshots.
- Only five pilot snapshots are promoted in this implementation. Do not auto-fill slots 6–30.
- Campaign slots are stable, positive, contiguous among promoted entries, and use zero-padded ids `campaign-NNN`.
- Campaign is completion-only: no stars, timer grading, move grading, or score.
- Level Select and onboarding tests assert behavior, not pixel coordinates or final art.
- Existing `?level=<n>` technical playtest and dev-only `?seed=<uint32>&candidate=<id>` generated playtest must continue to work.
- Dev launches must not load or mutate campaign progress.
- Save corruption must not crash the game; save failure must not undo in-memory progress or suppress a solved-level result.
- Promotion validates all gates before filesystem mutation and writes deterministic source with no timestamps or environment-specific paths.
- In this project's ZIP-overlay workflow, do not ask the user to commit intermediate micro-steps. Internal agentic worktree commits are allowed; the user-facing commit happens only after the final verification gate is green.
