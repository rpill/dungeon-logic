# Dungeon Logic — Project Definition

## 1. Концепция

Dungeon Logic — браузерная логическая puzzle-игра для Яндекс Игр.

Основное вдохновение механикой — Dungeons & Diagrams из Last Call BBS.

Цель — взять сильное дедуктивное ядро этой механики и адаптировать его под более широкую браузерную аудиторию:

* быстрое понимание;
* короткие игровые сессии;
* постепенное обучение;
* понятная визуальная обратная связь;
* большое количество уровней;
* ежедневные задания и другие retention-механики.

Игра не должна ощущаться как калька интерфейса Last Call BBS.

---

# 2. Fantasy theme

Игрок занимается восстановлением или исследованием маленьких fantasy-подземелий.

Решённая логическая сетка должна восприниматься не просто как закрашенный puzzle, а как настоящее небольшое подземелье.

Основной визуальный набор:

ORYX Ultimate Fantasy 1.2.

Предполагаемые игровые объекты:

* dungeon floor;
* stone walls;
* monsters;
* treasure chests;
* doors;
* props;
* adventurer;
* decorative dungeon elements.

На первом этапе использовать только то, что непосредственно улучшает читаемость головоломки.

---

# 3. Основной игровой цикл

Игрок получает незаконченную карту подземелья.

На поле уже могут находиться:

* монстры;
* сокровища;
* другие специальные элементы.

По краям поля находятся числа.

Игрок должен определить:

* где расположены стены;
* где остаётся проходимое пространство.

Для решения необходимо одновременно учитывать все правила уровня.

После правильного решения игрок получает состояние победы и может перейти к следующему уровню.

Основной долгосрочный режим называется **«УРОВНИ»**: один плоский каталог из 64 задач без глав и рукописей. Все пройденные задачи остаются доступны для replay; дополнительно одновременно открыты первые три ещё не решённых уровня. Карточка уровня показывает миниатюру: пройденные — каноническое решение, начатые — сохранённые игроком стены, не начатые — `?`; номер уровня расположен под миниатюрой.

Daily — отдельный режим. В билде заранее хранится 365 статических Daily на последовательные trusted UTC даты; слово «архив» используется только для уже прошедших Daily.

---


## 3.1. Актуальный onboarding / Daily UX

- Tutorial — отдельный короткий режим перед основными уровнями. Он учит действиями, а не длинными текстовыми инструкциями.
- Первый tutorial начинает с clue `0`: гарантированный пол предлагается отметить как `FLOOR`, после чего объясняется, что Floor — необязательная рабочая пометка, а победа определяется правильной расстановкой стен и выполнением правил.
- Monster tutorial обязан показывать не только вынужденные стены, но и единственный допустимый выход монстра как Floor.
- Daily имеет сегодняшний соревновательный пазл и архив прошлых Daily. В рейтинг идёт только первое самостоятельное прохождение сегодняшнего Daily.
- Hint в сегодняшнем Daily закрыт первые 5 минут; помощь после этого разрешена, но прохождение становится вне рейтинга. Архивные Daily не рейтинговые и используют обычные подсказки.
- Бесплатные подсказки восстанавливаются до запаса 3 по одной каждые 30 минут; rewarded ad позволяет получить конкретную подсказку без ожидания.

# 4. Состояния клетки

Базовая клетка может находиться в одном из состояний:

UNKNOWN

Игрок ещё не определил состояние клетки.

WALL

Игрок считает клетку стеной.

FLOOR

Игрок явно отметил клетку как свободное пространство.

Некоторые клетки могут быть фиксированными и не редактироваться:

MONSTER

TREASURE

и другие специальные типы в будущем.

Внутреннее состояние данных и визуальное представление клетки не обязательно должны быть одним и тем же enum.

---

# 5. Числа строк и столбцов

Каждая строка имеет число, определяющее необходимое количество стен в этой строке.

Каждый столбец имеет число, определяющее необходимое количество стен в этом столбце.

Пример:

строка длиной 6 клеток имеет clue = 3.

Значит, в правильном решении ровно три клетки этой строки являются стенами.

Во время игры UI должен показывать игроку прогресс выполнения ограничения.

---

# 6. Пустое пространство

Каждая клетка, которая не является стеной, относится к пространству подземелья.

Пустое пространство состоит из:

- hallways;
- treasure rooms.

Клетки с монстрами и сундуками логически являются не-стенами и занимают клетки пространства подземелья.

Все не-стены должны образовывать одну общую связную область.

Соседство считается только ортогонально:

- вверх;
- вниз;
- влево;
- вправо.

Диагональные клетки не считаются соединёнными.

---

# 7. Hallways

Hallways всегда имеют ширину ровно в одну клетку.

Следствие этого правила:

вне treasure rooms не может существовать полностью открытого блока 2×2.

То есть любой блок 2×2 из четырёх не-стен допустим только в том случае, если он является частью корректной treasure room.

Нельзя проверять правило 2×2 изолированно от правил treasure room.

---

# 8. Монстры и тупики

Каждый монстр находится в тупике.

Каждый тупик содержит монстра.

Для hallway-клетки тупик означает, что у неё существует ровно один ортогонально соседний проход.

Следовательно:

- нельзя иметь монстра в обычном проходе с двумя или более выходами;
- нельзя иметь обычный hallway dead end без монстра.

Treasure room не является hallway, поэтому её внутренние клетки не должны интерпретироваться как hallway dead ends.

---

# 9. Treasure rooms

Treasure room всегда имеет размер ровно 3×3 клетки.

Каждая treasure room:

- состоит из девяти не-стен;
- имеет ровно один вход;
- содержит ровно один сундук.

Сундук может находиться в любой из девяти клеток treasure room.

Положение комнаты не задаётся напрямую игроку.

Игрок должен определить расположение treasure room исходя из:

- положения сундука;
- row clues;
- column clues;
- расположения монстров;
- остальных правил подземелья.

Один вход означает единственное ортогональное соединение между клетками treasure room и hallway вне этой комнаты.

Treasure room является исключением из правила ширины hallways и запрета открытого 2×2.

---

# 10. Решение уровня

Уровень считается решённым только тогда, когда одновременно выполнены все правила:

1. В каждой строке находится ровно столько стен, сколько указано её row clue.
2. В каждом столбце находится ровно столько стен, сколько указано его column clue.
3. Все не-стены образуют одну ортогонально связанную область.
4. Каждый монстр находится в hallway dead end.
5. Каждый hallway dead end содержит монстра.
6. Каждый сундук принадлежит корректной treasure room 3×3.
7. Каждая treasure room содержит ровно один сундук.
8. Каждая treasure room имеет ровно один вход.
9. Вне treasure rooms hallways имеют ширину одну клетку.
10. Вне treasure rooms отсутствуют полностью открытые блоки 2×2.

Скрытое solution может храниться в данных уровня для разработки и проверки, но игровой feedback не должен просто сравнивать действия игрока с solution.

Игрок должен получать информацию на основании публичных правил головоломки.

---

# 11. Угадывание

Цель дизайна уровней:

каждый уровень должен иметь единственное решение и позволять прийти к нему логическим путём.

Игрок не должен быть обязан выбирать случайный вариант между двумя равноправными решениями.

Solver и автоматическая проверка уникальности решения будут сделаны позже.

# 12. Управление

## Desktop

### Left Mouse Button

ЛКМ ставит или убирает стену.

- UNKNOWN → WALL;
- FLOOR → WALL;
- WALL → UNKNOWN.

Если зажать ЛКМ и провести по клеткам, игрок рисует стены одним непрерывным мазком.

Если мазок начинается на WALL, режим меняется на стирание стен.

Во время стирающего мазка удаляются только WALL-клетки.

### Right Mouse Button

ПКМ ставит или убирает явную отметку свободного пространства.

- UNKNOWN → FLOOR;
- WALL → FLOOR;
- FLOOR → UNKNOWN.

Если зажать ПКМ и провести по клеткам, игрок отмечает свободные клетки одним непрерывным мазком.

Если мазок начинается на FLOOR, режим меняется на стирание FLOOR-отметок.

Во время стирающего мазка удаляются только FLOOR-отметки.

### Drag

В пределах одного мазка одна клетка обрабатывается не более одного раза.

Повторное проведение курсора через уже обработанную клетку не должно переключать её состояние повторно.

### Fixed cells

MONSTER и TREASURE/CHEST являются фиксированными открытыми клетками.

Игрок не может превратить их в стены или удалить.

### Planned controls

Позже могут быть добавлены:

- touch;
- keyboard shortcuts;
- Undo;
- Restart.

# 13. Ошибки

На раннем этапе игра не должна автоматически наказывать игрока за каждую неправильную гипотезу.

Игрок должен иметь возможность рассуждать и менять свои отметки.

Не следует сразу подсвечивать каждую клетку, которая не совпадает со скрытым solution.

Это превращает логическую игру в подбор ответа.

Допустимо показывать нарушения уже известных публичных правил, например:

* в строке поставлено слишком много стен;
* монстру физически невозможно оставить один выход.

Система ошибок будет уточняться после первого прототипа.

---

# 14. Difficulty progression

Обучение вынесено в отдельную Tutorial-главу до Campaign. Campaign не должен одновременно быть учебником и обычной прогрессией.

Tutorial v2 состоит из пяти маленьких fully-guided пазлов, каждый из которых вводит ровно один новый принцип:

## Tutorial 1 — Числа и ПОЛ

Поле 3×3. Сначала `0 → FLOOR`, затем точное количество стен в строке/столбце. `FLOOR` явно объясняется как необязательная пометка; победа определяется правильными стенами.

## Tutorial 2 — Монстры и тупики

Сначала применяются уже знакомые числа. Правило монстра появляется только тогда, когда оно действительно даёт новую дедукцию: у монстра остаётся один выход. Обратное правило «любой тупик содержит монстра» тоже показывается действием.

## Tutorial 3 — Связность

После обычных clue/monster-дедукций создаётся единственная клетка-мост между двумя областями пола. Только в этот момент объясняется, что весь проход должен быть связан по сторонам, а диагональ не соединяет клетки.

## Tutorial 4 — Коридоры / 2×2

Правило открытого `2×2` показывается только после того, как три клетки конкретного квадрата уже реально отмечены `FLOOR`; четвёртая тогда однозначно становится `WALL`.

## Tutorial 5 — Комната с сундуком

Сундук впервые появляется здесь. Игрок отмечает очевидную комнату 3×3 как `FLOOR`, затем через числа и уже знакомые правила формирует её границы и в конце применяет правило единственного входа.

Во всём Tutorial нет standalone message-step: каждый текст привязан к конкретному действию на поле и сам переключается после выполнения этого действия. Ни одна обучающая плашка не блокирует поле или таймер.

Ключевой педагогический принцип: нельзя просить поставить `WALL/FLOOR` только потому, что так выглядит hidden solution. Активный текст обязан объяснять дедукцию, которая уже следует из видимого состояния поля.

После Tutorial начинается самостоятельная Campaign. Дальше размер поля и длина дедуктивных цепочек постепенно увеличиваются.

# 15. Размеры поля

Первый прототип:

6×6.

В дальнейшем рассматриваются:

* 5×5;
* 6×6;
* 8×8;
* 10×10;
* 12×12.

Размер является одним из факторов сложности, но не единственным.

---

# 16. Visual feedback

Игрок должен моментально видеть различие между:

* unknown;
* wall;
* floor;
* fixed cell;
* monster;
* treasure.

Clue также должен визуально отражать:

* ещё не выполнено;
* выполнено;
* превышено.

Однако яркая красная ошибка не должна появляться просто потому, что игрок временно сделал неправильную гипотезу.

---

# 17. Победа

После успешного решения:

1. блокируется редактирование;
2. появляется короткая визуальная реакция;
3. служебная puzzle-разметка может немного отходить на второй план;
4. игрок видит получившееся подземелье;
5. появляется переход на следующий уровень.

В будущем можно добавить короткую сцену с adventurer, проходящим построенное подземелье.

Это не входит в первый vertical slice.

---

# 18. Первый Vertical Slice

Первый playable prototype должен содержать только:

* Phaser;
* TypeScript;
* одно поле 6×6;
* один вручную заданный уровень;
* row clues;
* column clues;
* monsters;
* unknown/wall/floor;
* mouse input;
* Undo;
* Restart;
* проверку количества стен;
* проверку monster dead-end rule;
* проверку connectivity;
* проверку 2×2;
* определение победы;
* минимальный ORYX visual pass.

Не входят:

* генератор;
* solver;
* campaign map;
* daily;
* monetization;
* Yandex SDK;
* achievements;
* leaderboards;
* inventory;
* economy;
* animated adventurer.

---

# 19. Принцип разработки

Сначала необходимо доказать, что сама головоломка:

* понятна;
* приятна;
* хорошо читается;
* вызывает желание решить следующий уровень.

Все системы retention и monetization добавляются только после работающего puzzle-core.
